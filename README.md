# qizo

A from-scratch operating system for x86-64, written to make low-end chips feel fast.
Every line of code and every asset in this repository is generated by Arena.ai Agent Mode
for maintainers Arunkumar (Seigh-sword) and Surya (suripewepedi).

qizo v0.1.0 boots to a shell. Nothing more, nothing less: no drivers nobody asked for, no
VFS abstraction layers, no compatibility code. The whole bootable image is 2.2 MiB and the
compressed artifact is 26 KiB.

```
qizo.img      2.2 MiB   hybrid MBR disk: stage1 + stage2 + compressed kernel + FAT
qizo.img.xz     26 KiB   what you actually download
qizo.iso      2.2 MiB   El Torito CD image wrapping the same disk
qizo.iso.xz     26 KiB
kernel        33 KiB    flat load image, 128 KiB budget with .bss
```

## Build

Requirements: gcc, binutils (as/ld/objcopy/nm), make, python3, xz. Nothing else. No nasm,
no grub, no xorriso, no loop devices, no root.

```sh
make            # build everything, including compressed artifacts
make check      # validate the boot chain, the filesystem, the ISO and the handoff
make test       # unit tests for the container format, font and memory layout
make clean
```

`make ARCH=native` tunes the kernel for the build machine.

## Run

```sh
qemu-system-x86_64 -m 64 -drive file=build/artifacts/qizo.img,format=raw,if=ide \
    -display none -serial stdio -monitor none
```

Serial output and the VGA text console show the same shell. `help` lists the commands:
`info`, `cpu`, `mem`, `bench`, `micro`, `ticks`, `speed`, `about`, `clear`, `reboot`.

## How it boots

```
LBA 0        stage1 (MBR, 448 byte budget)      boot/qizo/stage1.S
LBA 16       stage2 code (4 KiB, 0x20000)       boot/qizo/stage2.S
LBA 24       module blob (LZSS + adler32)       tools/mkqizoimg
LBA 58+      FAT volume (read-only, README + KERNEL.BIN)
```

stage1 loads `[stage2 | blob]` with INT 13h extended reads, jumps to 0x20000. stage2 enables
A20, reads the E820 map, checks the adler32 of the blob, decompresses the kernel with an
in-place LZSS decoder, verifies the module header, drops into protected mode, builds 2 MiB
page tables, flips into long mode and jumps to the kernel with a bootinfo block. The kernel
installs its own page tables (1 GiB identity plus a 1 GiB higher half direct map), sets up
the serial port and the VGA text console, the frame allocator, the IDT with the timer and
keyboard, then starts the shell.

There is no ELF loader at boot: the kernel is a flat image plus a 64 byte module header.
Details and the full memory map are in [docs/BOOTING.md](docs/BOOTING.md).

## Layout

```
boot/            stage1 (MBR), stage2 (loader + LZSS decoder + long mode handoff), linker scripts
kernel/          64-bit handoff, console, cpu features, physical memory allocator, IDT, PS/2, shell
kernel/lib/      freestanding libc and hand written SSE2 copy/fill
tools/           image builder, ISO builder, boot verifier, font and header generators
tools/common/    shared layout constants, LZSS codec, font definitions
.github/         CI: build, test, validate, QEMU boot smoke, release
docs/            boot contract, development guide, roadmap
```

`boot/qizoboot.inc` is the single source of truth for every address and offset. The C side is
generated from it (`tools/qizoartifacts/qizobootinfo.py`) and checked with `_Static_assert`,
so the bootloader and the kernel can never disagree about the handoff.

## Design rules

- The kernel is meant to be a beast: hand written decompression, 2 MiB pages, SSE2 memory ops,
  no heap allocator at boot, no paging rework per allocation, no per-character MMIO reads.
- Nothing heavy gets added just because it is popular. Each subsystem has to pay for itself.
- Zero binary blobs: the boot chain is our own assembly, the font is generated from column
  data committed in `tools/common/qizofont.py`.
- No third party build tools. If a host has gcc, binutils, make, python3 and xz, it can build qizo.
- No code comments and no emoji in sources: names and structure carry the meaning.
